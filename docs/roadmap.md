# Roadmap

## Planned

1. **More apps as tool sources.** Nunsori is the first app whose tools the chat uses (`FileIndex`). A notes app (see Nunsori's roadmap) should offer its own tools through a similar contract; the chat would then list tools per connected app.
2. **Web tools (lowest priority).** Web search and fetching a page for the chat model. They go against the on-device principle (queries and page requests would leave the phone), so they come after the rest. If built: off by default, a clear disclosure of what leaves the device, a search API choice, and the network part in a separate component, since this app has no `INTERNET` permission.
3. **Restore from trash** for documents Nunsori moved to `.LSA_Trash`.

## Other ideas (from Nunsori's roadmap before 0.10.0)

- **Sub-agent for images:** the chat model cannot look at an image that a tool returns (tool results are text only), so a search hit that is a photo stays a file name and OCR text. Idea: a tool such as `describe_image(item_id, question?)` that starts a separate, short model call (a sub-agent with its own small prompt and no tools) that does see the image, and hands back a summary or description (optionally answering a specific question about it) as the tool result. The same pattern could serve other jobs that would clutter the main context (summarize a long document, check one file against a condition). Open points: which model does it (the chat model when it has vision, otherwise a vision-capable one) and the memory cost of loading it next to the embedder Nunsori uses (memory is managed by OndolSaem), latency on a phone (one call per image, so a cap per turn), caching descriptions per file so they are not recomputed (possibly reusing them as search text, which would touch Nunsori's indexing pipeline), a prompt that keeps descriptions short for the 4K window, and whether scheduled runs may use it (battery).
- **Agent skills for the chat:** reusable instruction bundles (a name, a one-line description and a Markdown body, in the spirit of agent skills) that the user can add, edit and switch on per chat or for scheduled tasks. Sketch: the system prompt lists only each active skill's name and description; a small tool (for example `use_skill`) returns the full body when the model decides it applies, so the context cost stays low on the 4K default window. Open points: where skills live (app storage, imported from a folder or a shared file), a few built-in examples (receipt summary, weekly digest), how a skill may refer to the existing tools, whether scheduled runs can use them, and a size limit per skill. Skills stay plain text; they never run code.
- **More reliable tool calls with the small chat model:** seen on the emulator with Gemma 4 E2B: for "When a photo of a business card is added, add the person to my contacts" the model called `schedule_task` without the required `trigger` argument, got `Error: trigger must be time or file.` and still told the user "I have scheduled a task … please confirm", although no task card existed (a second try with "Schedule a file task: …" worked). Ideas: infer a missing `trigger` (a `query`/`kinds` argument means a file task, a time argument means a time task) in `TaskManager.propose`; return a more actionable error that lists the arguments and an example call; let `ChatController` retry once when a tool returns an error before the model may answer, or show the failed call as an error card so the user is not told something succeeded; add a test with the failing argument shapes. Check the same for the other write tools (`add_contact`, `add_calendar_event`, `move_files`).
- **File-type filter of file-triggered tasks seems not to hold (to investigate and fix):** with a request such as "only photos of …" the task appears to fire for every new file, not just the named kind. In the emulator test the confirmation card read "When a new  file matching …" with an empty kind, so the model may not pass `kinds` at all (it is optional in the `schedule_task` schema, see `ScheduleTools`), or the filter in `TaskManager.onIndexChanged` / `fileTask` may not be applied to the candidates. To check: what `kinds` the model sends for "photo", "document" and similar words, what `fileKinds` is stored, and whether `onIndexChanged` filters by it before the match and the *Let the assistant judge new files* path (which queues every new file with text when there are few). Ideas: show the kinds on the card ("new image matching …"); infer `kinds` from words in the instruction when the model leaves it out (photo, picture, image, PDF, document, recording, video); a test per kind that checks a non-matching file never becomes a candidate.
- Chat: attach arbitrary files that are not indexed (text extraction on the spot), NPU/GPU choice, summaries for long chats instead of dropping old messages.

## Limits

- Small models can pick the wrong tool or arguments (see [chat.md](chat.md#models-and-limits)).
- File tasks run after Nunsori indexed a file, not when it appears; a missed hint waits for the next app start or the daily check.
- Re-indexed files (after a model change in OndolSaem) count as new for file tasks.
- The small default chat model sometimes calls a tool with missing arguments (for example `schedule_task` without `trigger`) and then claims success; check that a task card appears (see the idea above).
- Scheduled tasks run one at a time and need the chat model, so a run can be late when another answer is being generated or the phone is in Doze or an OEM sleep list (Samsung *Sleeping apps*); a new file counts only if it clearly stands out from the typical similarity of Nunsori's index (or contains all the query words) and the chat model confirms it; photos without text are not checked by the model.
